## 四、⭐ 本轮唯一待办：proxy 内存索引仍是 558

| 证据 | 值 |
|---|---|
| 磁盘 `index.json` | **559** |
| proxy `/health` | `inexbot: {"docs": 558}` ← **旧索引** |
| proxy 进程启动 | 2026-11-05 11:02:57（**早于**本轮采集 2026-11-06 11:05） |
| reload 链 | **存活**（`schedule_reload()` 的 `try/except/finally` 补丁在位，进程 3 线程） |
| 下次自动重载 | 启动后 5h → **约 12:03 今天**（`RELOAD_INTERVAL=18000s`） |

**判读**：这**不是**「补丁没上线」故障，而是**正常的 5 小时重载窗口**。
新页在 12:03 会被自动载入，无需干预。

**⏱ 重载链存活性证明（2026-11-06 新方法）** —— 不看 journal（stdout 块缓冲），
改看**线程的 starttime**：

| 线程 | 出生时间 | 含义 |
|---|---|---|
| tid=1844673（主线程） | 2026-11-05 11:02:58 | proxy 进程启动 |
| **tid=1853958** | **2026-11-06 07:03:19** | **reload 定时器线程** —— 它在 07:03 触发过一次（= 主线程启动 +5h），并已排下下一次 |
| tid=1857635 / 1857758 | 11:20 / 11:22 | e2e 请求的工作线程（短命） |

主线程启动 11:02:58 + 5h = 16:02:58 的第一次重载 **没有发生**（因为 07:03 已经是第一次，
说明实际排期基准是**定时器线程自身的出生时刻**）。
由 tid=1853958 的出生时间 + 5h ⇒ **下次重载 = 2026-11-06 12:03:19**（本轮实测时约 39 分钟后）。

> 💡 **方法论**：判断「重载链是否断裂」的最可靠手段是
> **看有没有一个 age ≈ 4~5 小时的长命线程**（定时器每次触发都会新建一个 `threading.Timer`）。
> 链断了 → 不再有这种 age 落在 5h 附近的线程 → proxy 永远停在旧索引。
> 可复用脚本见本轮 `/tmp/check_reload_timer.py`（读 `/proc/<pid>/task/*/stat` 的第 22 字段）。
> ⚠️ 别用 journal 里有没有 `Total:` 来判（stdout 块缓冲，陷阱：journal 看不到 ≠ 没重载）。

**⚠️ 但本轮未主动 restart**，原因有二：
1. 姊妹 KB 的 e2e 探针（PID 1855683）在跑 → restart 会把它打成 `RemoteDisconnected`（陷阱 1 / 陷阱 20）
2. 自动重载在 1 小时内就会发生，**主动 restart 收益为零、风险为正**

⇒ 下轮 cron（11-07）开工时先查 `/health` 的 `docs` 是否 = 559；
若仍 = 558，说明**重载链断了** → 按上面的「线程 age」方法复核 `schedule_reload` 的 `finally` 是否被回退。
