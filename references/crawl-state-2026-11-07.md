## 四、⭐ 本轮核心发现：`check_reload_timer.py` 是个**假阳性发生器**（已修）

11-06 那轮新写了 `scripts/check_reload_timer.py`，用「找 age 落在 **5h 附近**的线程」
来判「重载链是否存活」。**本轮实测它报 `[FAIL] 重载链可能已断裂`——但链是好的。**

| 证据 | 值 |
|---|---|
| 脚本报的线程 age | **2.97h**（定时器 08:03:33 出生 → 下次 13:03:33） |
| 脚本的判定窗口 | `age ∈ [3.5h, 5.25h]` → **2.97h 落在窗口外** |
| `/health` | `inexbot: {"docs": 559}` |
| 磁盘 `index.json` | **559** 条 |
| proxy 源码 `schedule_reload()` | `try/except/finally` **完整在位** → 链是活的 |

**根因**：定时器线程在**上次触发时出生**，活满一个 `RELOAD_INTERVAL`（5h）后再次触发
⇒ 它的 age **恒定落在 `[0, 5h)` 且在周期内均匀分布**。
⇒ 「找 age 落在 5h 附近」这个窗口只覆盖了 30% 的时间，**约 70% 的时间会误报「链断了」**。

**危害**：误报会让下一轮 cron 去 `restart hermes-skill-proxy.service` ——
而 restart 会打断姊妹 KB 正在跑的 e2e 探针（陷阱 1 / 陷阱 20），
**收益为零、风险为正**（这正是 11-06 拒绝 restart 的理由，却差点被脚本带偏）。

**✅ 修复（已提交 `4d78599`）**：

1. 定时器 = **age < RELOAD 的非主线程里最老的那一个**（请求工作线程都是秒级短命）
2. **交叉验证**：`/health` 的 `docs` 是否等于磁盘 `index.json` 条目数 ——
   相等就**证明**重载发生过，链必然活（ground truth）
3. 只有「**既没有 age<5h 的非主线程**」**且**「内存 ≠ 磁盘」**才判 FAIL

修复后实测输出：

```
[OK] 重载链存活：定时器线程 tid=1871807
  -> 上次触发 2026-11-07 08:03:33
  -> 下次重载 2026-11-07 13:03:33  (在 122 分钟后)
  -> 内存/磁盘同步: 是
```

> 💡 **方法论**：**探针本身也会制造假阳性** —— 写完判据先用**已知健康**的
> proxy 跑一遍。若报 FAIL 但 `/health` 的 docs 与磁盘一致，**是脚本错了，不是 proxy 错了**。
> 已写入 `references/shared-proxy-service-pitfalls.md` §陷阱 21。
